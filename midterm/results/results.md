## 1. Итог и выбранная стратегия

Основной кандидат — **`submissions/hybrid.csv`**: MAP@5 на truth top-10 = **0.418000**. Лучший одиночный метод — PPR: **0.414050**. Popularity: **0.277444**, личная история: **0.405529**. Реализованы два требуемых алгоритма сверх бейзлайнов: Personalized PageRank на co-view графе и implicit ALS на NumPy.

Гибрид выше PPR на 0.003950 абсолютных единиц (0.95% относительно PPR). Парный bootstrap по пользователям, 2000 выборок, seed=20261024: 95% интервал разницы [-0.001588; 0.009564]. Это описательная оценка на том же hold-out, на котором выбирались параметры, а не независимое подтверждение выигрыша. ### Правило сопоставления

Одинаковый канал: `vsetv_id = channel_id`. Интервал просмотра `[start_time, stop_time]` пересекается с `[start, start+duration)`; вес пересечения — `max(0, min(stop_time, start+duration) − max(start_time, start))`. В непрерывных секундах включение правой границы просмотра не меняет длительность; касание границы даёт ноль. Перед join объединены расписания 11–20 и 21–30, удаляются дубли по `(channel_id, start, end, tv_show_id)`. Фактически удалено **0**; строк с неположительной длительностью эфира исключено **1**. Интервалы, пересекающие границу split, разрезаются по ней; каждая секунда попадает в соответствующее окно. Используются наивные локальные даты без выдуманного timezone shift. Лог читается чанками по 250000 строк; расписание индексируется по каналу, префиксу максимального конца и `searchsorted`. Сумма секунд всех положительных пересечений агрегируется в одну запись пользователь×программа за окно.

`tv_show_id=0` — не айтем, не пользовательская фича и не рекомендация. Такие пересечения считаются только в аудите. Покрытие расписанием и доли размеченных/нулевых секунд вычислены по **объединению интервалов** каждого канала, поэтому перекрывающиеся строки расписания не удваивают знаменатель. ### Порог «посмотрел»

Основной порог фиксирован **60 секунд суммарно на пользователь×программа за окно обучения**. После него остаётся 842387 пар (из 856904). Это абсолютный cut, не процент длительности передачи. Он отсекает короткие пересечения границ эфира, но сохраняет краткие информационные передачи и повторные короткие заходы. Truth фиксирован независимо от обучающего cut: top-10/top-5 по всем положительным секундам и отдельный вариант ≥1800 с. Это позволяет проверять чувствительность обучения без подмены цели.

## 4. Зафиксированный протокол валидации

- Train: `[2020-03-09 00:00:00, 2020-05-18 00:00:00)` (недели 11–20); validation: `[2020-05-18 00:00:00, 2020-07-27 00:00:00)` (21–30). Все модели обучены на взаимодействиях **всех** пользователей train; оценка — только на пользователях template, в исходном порядке.

- Кандидаты валидации: **6384** id≠0, эфир которых пересекает окно validation. Поэтому их количество не обязано равняться числу уникальных id в одном CSV: слот из предыдущего файла может пересечь границу. Повторы уже просмотренных программ разрешены одинаково для всех методов. Финальное окно: `[2020-07-27, 2020-10-19)` (31–42); кандидаты из `export_arh_31-42-final.csv`: **6632**. Расписание теста читается только для этого множества и учёта строк; его названия, жанры, актёры и частоты эфира не входят в модели.

- Основная релевантность: десять программ пользователя с наибольшими суммарными секундами в validation; дополнительная: top-5 и все программы с ≥1800 с. При равенстве секунд — меньший id. Ранжирование truth нужно только для выбора множества: внутри AP релевантность бинарная, не duration-weighted.

- `AP@5 = Σ_{r=1..5}(P@r × rel_r) / min(5, |truth|)`; для пустого truth AP=0. MAP — среднее по **всем 1260** пользователям, без исключения холодных или пустых. непустых top10: 1246; непустых top5: 1246; непустых ge1800: 1244.

- Холодных пользователей при пороге 60 с: **10**. Единый fallback — общий popularity train, ограниченный текущими кандидатами. Если модель даёт меньше пяти положительных конечных score, остальные позиции заполняются тем же popularity без повторов. Равные score — по возрастанию id. Результат — ровно пять уникальных ненулевых id. Для холодных пользователей все пять методов дали идентичные списки (проверено по сохранённым предсказаниям).

- Только train-секунды входят в веса/граф/факторы. Validation-секунды используются для truth и выбора параметров, не для fitting в валидационном эксперименте. На этапе финального refit недели 21–30 включаются в обучение. Общий массив id — лишь индекс для выравнивания; у будущих/неизвестных обучению id нет взаимодействий и обученного сигнала. Названия и категории для таблиц берутся только из расписаний 11–30 и не используются алгоритмами.

## 5. Методы и гиперпараметры

**Popularity:** сумма секунд программы по всем train-пользователям после порога. **Личная история:** собственные суммарные train-секунды, затем общий fallback. Это сильный repeat-aware бейзлайн для сериалов и регулярно выходящих передач; он не ищет похожих пользователей.

**PPR:** взвешенная матрица `L_ui=log1p(seconds_ui/60)` нормируется L2 по пользователям; `G=L.T@L`, диагональ обнуляется, затем cosine-нормировка по столбцам L. Для каждого айтема сохраняются 50 сильнейших исходящих соседей (ties по id), после чего строки графа нормируются к вероятностям. Изолированным вершинам добавлена петля. Персональный restart `r_u` пропорционален исходным секундам собственной истории, а не валидационным просмотрам. Итерации `p=(1−alpha)r + alpha P.T p`; alpha — вероятность продолжить прогулку, restart probability — `1−alpha`. Stop: максимальное по пользователям L1-изменение <1e−6, максимум 200 итераций. Граф: 9669 вершин (включая изолированные id индекса), 155197 рёбер с петлями.

**Implicit ALS:** минимизируется `Σ_ui c_ui(p_ui−x_u·y_i)^2 + λ(Σ||x_u||²+Σ||y_i||²)`. `p_ui=1` для пар после cut, иначе 0; ненаблюдаемые пары имеют `c_ui=1`. Для просмотренных `c_ui=1+scale*f(seconds_ui)`, где `f=log1p(seconds/60)` либо `seconds/3600`. Обновления — точные normal equations через `numpy.linalg.solve`; отсутствующие пары учтены через полный Gram. 15 полных итераций user/item updates, λ=10, начальные факторы `Normal(0,0.01)`, фиксированный seed. Пользователь/айтем без взаимодействий получает нулевой фактор. Score — dot product; это не вероятность. Отрицательные score не используются для заполнения рекомендаций: действует единая положительность + fallback.

Итог — взвешенная сумма четырёх rank-score: история, PPR, ALS, popularity. Сырые секунды, вероятности прогулки и dot products напрямую не складываются. ## 7. Два пользователя: история, рекомендации, фактическое поведение

Выбор сделан без просмотра успеха рекомендаций: 90-й и 10-й процентили суммы размеченных train-секунд среди template-пользователей с пригодной train-историей и непустым validation truth. «Тяжёлый» и «лёгкий» — относительная интенсивность **размеченного** просмотра на этой платформе. Ниже одни и те же пользователи для всех методов. В общую таблицу добавлены сохранённые validation top-5 Iteration 3; финальные списки 31–42 показаны отдельно. Название и категория — представительная запись расписания 11–30 для id (первая после сортировки по каналу и времени). Один id может объединять разные сезоны/эпизоды с разными заголовками, поэтому конкретный номер серии в таблице не означает рекомендацию именно этого эпизода.

## 8. Бизнес- и алгоритмический выбор (§8)

Для офлайн-цели этой задачи я выбираю **rank-fusion историю + PPR + ALS + небольшую popularity**, поскольку он лучший по основной MAP и по дополнительному truth ≥1800. Для практического запуска преимущество над PPR следует считать предварительным: bootstrap и альтернативный top-5 не дают основания обещать устойчивый рост. PPR — сильный более простой резервный вариант; история — дешёвый обязательный контроль качества. Привычные регулярные передачи важны в ТВ, поэтому исключать повторы здесь означало бы менять пользовательскую задачу.

Popularity уже находит массовые регулярные передачи без профиля и даёт одинаковый осмысленный старт холодным пользователям, но проваливается на двух выбранных пользователях по top-10. История лучше сохраняет индивидуальную длительность и повторный спрос. PPR переносит часть массы на co-view соседей и дальше по графу; при слишком большом alpha персональный restart слабее, а качество основной цели в измеренной сетке снижается. ALS сжимает совместный просмотр в низкоранговые факторы: в текущей сетке его списки существенно слабее и более массовые, чем repeat-aware история. Это результат данного обучения, не доказательство общей непригодности MF для ТВ. Ассоциативные правила могли бы явно выделять направленные связи с support/confidence/lift и редкие локальные сочетания, которые низкоранговое сглаживание теряет; здесь такие правила не строились. Content-признаки category/genre/year/director/actors могли бы связывать новые программы при отсутствии co-view сигнала, но это гипотеза дальнейшей работы: content-модель не реализована, её прирост не измерен.

На данном масштабе sparse-граф и история недороги относительно полной сетки ALS; в production можно пересчитывать граф/факторы пакетно, а онлайн хранить top-кандидатов и выполнять лёгкую rank-fusion. Измеренное время ниже относится к пакетному Python-прогону на этом компьютере, не к latency сервиса. Два примера показывают преимущественно знакомые предпочтения; один новый для train id у ALS получил наблюдаемый просмотр в дополнительной цели, но это ещё не измерение удовлетворённости или полезности открытия. Выбор смеси повышает среднее качество, но не гарантирует разнообразие или лучший опыт каждому зрителю. Онлайн A/B-тест, выручка, удержание и удовлетворённость не измерялись и не заявляются.

## 11. Ограничения и границы выводов

1. Основное ограничение — большая часть строк эфира не имеет id. Покрытие эфирных секунд и просмотренных секунд отличается от доли строк; все три величины приведены выше. Мы предсказываем только размеченное поведение, а не весь интерес пользователя.
2. Один временной hold-out использован для выбора alpha, ALS и fusion. Это оптимистичная оценка выбранной стратегии; нужна следующая временная проверка или nested rolling validation. 60-комбинационная сетка fusion усиливает selection bias.
3. Эфирная доступность известна заранее, но пользовательские часовые пояса, подписки/доступность каналов и возможность одновременно смотреть передачи не моделируются. Программа агрегирована по id, а не по эпизоду/конкретному показу.
4. Просмотр не равен удовлетворённости; длительность может отражать фоновый телевизор. Перекрывающиеся устройства и лог-дубли не превращены в уникальное человеческое время.
5. Неизвестные обучению программы без content-сигнала не имеют персонального пути в PPR/ALS; popularity тоже не знает их спроса. Они могут попасть только через нулевые tie/fallback, что не решает item cold-start содержательно.
6. Более высокий threshold улучшал некоторые модели, но основная постановка не менялась. Глобальное превосходство гибрида не переносится на каждого зрителя: тяжёлому примеру лучше служила история.
7. Не оценивались content-based, ассоциативные правила, recency decay, сезонность и channel-aware режим. Нельзя утверждать превосходство над этими альтернативами.
8. Метрика Kaggle и фактическое тестовое поведение не наблюдались. Офлайн MAP не выдаётся за public-score или бизнес-эффект.

## 16. Новые признаки и методы

### (a) Свежая популярность

`pop_recent_2w/4w/6w` — сумма секунд в последних полных 2/4/6 неделях до cutoff. Сначала агрегируется пара user×item внутри свежего окна, затем применяется тот же cut 60 с, затем суммируется по пользователям. Например, в новой валидации окна — недели 17–18, 15–18 и 13–18; в финале — 29–30, 27–30 и 25–30. По новой основной метрике выбран `pop_recent_6w`. На старой валидации лучше 2 недели, но это не использовано для замены нового выбора. Совпадающие MAP свежих/общих вариантов возможны: одинаковый top-5 не означает одинаковых полных score/rank.

### (b) Объём эфира целевого окна

После дедупликации `(channel,start,end,id)` считаются `N_i` — число выходов, пересекающих окно, и `D_i` — сумма секунд этих выходов, обрезанных границами окна, по всем каналам. Один показ на двух каналах считается двумя возможностями просмотра. Standalone: `air_count=N_i`, `air_duration=D_i`. Также проверены `popularity×N_i^γ`, `popularity×D_i^γ` и opportunity-adjusted `popularity×(D_target_i/max(D_train_i,3600))^γ`, γ∈{0.25,0.5,1}. Часовой floor защищает от чрезмерного деления на короткий слот у границы окна. Это гипотезы о возможности просмотра, не прогноз аудитории по самим расписаниям. Чистый объём эфира оказался слабым; прямое умножение на него обычно ухудшало popularity. Лучший новый вариант содержит малую долю schedule-rank в персональном гибриде; выигрыш не следует приписывать standalone airtime или единственной причине без абляции.

### (c) Популярность внутри любимых каналов/категорий

`channel_pop(u,i)=Σ_c q_u(c)×P_train(i|c)×1[программа i идёт на c в целевом окне]`. `q_u(c)` — доля **всех** train-секунд пользователя на канале, включая неразмеченный эфир; `P_train(i|c)` — доля секунд программы среди размеченного train-просмотра канала после общего user-item cut. Для категорий аналогично: `category_pop(u,i)=q_u(category_i)×P_train(i|category_i)`. Профиль категорий строится только по размеченным train-парам после cut, категория id — самая длительная по pre-cut расписанию (ties по алфавиту). `channel_category` — 50/50 reciprocal-rank fusion этих двух списков. Это мягкая смесь любимых контекстов без подбора числа favourite-каналов. Совершенно новые программы не получают спроса из этих conditional-pop моделей, хотя доступны для schedule-rank и fallback.

### (d) Гибрид и пространство выбора

Как в первой итерации, компоненты переводятся в top-100 rank-score `1/(20+r)` с общей popularity-добивкой. Новые компоненты fusion: all-time popularity, выбранный recent popularity, один персональный компонент (history/PPR/legacy_hybrid/channel_pop/category_pop/channel_category) и schedule count либо duration. Сетка: персональный вес ∈{0,0.25,0.5,0.75}, schedule-вес ∈{0,0.1,0.25,0.5}, оставшаяся масса — popularity. Доля recent внутри popularity ∈{0,0.5,1}; исключаются отрицательные остатки и дубли. Всего **315** уникальных конфигураций. При равной основной метрике сохраняется первая конфигурация сетки; old validation не используется как tie-breaker. Помимо общего победителя отдельно выбираются лучшие внутри семейства popularity≥50%, popularity≥50% со schedule>0 и popularity+schedule без персонализации. Это намеренно разные гипотезы для следующей проверки пользователем; ограничения семейства заданы до выбора весов.

## 23. Основа: каналы, категории, произведение и совместное условие

Обозначим `C(u,i)=Σ_c q_u(c) P_train(i|c) 1[availability(i,c)]`, `G(u,i)=q_u(g_i) P_train(i|g_i)`. Item/category и conditional popularity рассчитываются по размеченным train-взаимодействиям после общего cut. Категориальный профиль всегда взвешен секундами. Два канальных профиля используют все train-просмотры, включая эфир без id:

- **time:** `q_u(c)` — доля секунд исходных интервалов на канале; как в Iteration 2.
- **count:** `q_u(c)` — доля исходных записей просмотра на канале. Одна запись лога считается один раз независимо от числа затронутых программ или недель; её счёт относится к неделе начала (после обрезки началом общего диапазона). Это число сессий/записей в логе, не уникальные дни и не факт удовлетворённости. Запись, начавшаяся до cutoff и продолжившаяся после него, учитывается в count один раз; в time-профиле используются только секунды до cutoff.

Для count-профилей прочитаны все CSV-чанки, отобрано **2173313** исходных записей целевых пользователей; кеш — **540759** user×channel×week строк. Сумма counts до каждого cutoff независимо сверена при проходе по исходному логу:

## 24. Сглаживание с глобальной popularity

Каждый контекстный score сначала обнуляется вне кандидатов и нормируется по строке: `B_norm(u,i)=B(u,i)/Σ_j B(u,j)`. При нулевой строке остаётся ноль, затем действует общий fallback. Сглаживание: `(1−λ) B_norm(u,i) + λ Pop_norm(i)`, где Pop_norm — all-time train-seconds, нормированные по доступным кандидатам. λ∈{0,0.05,0.1,0.2,0.4,0.6}. Эти нормировки нужны для сопоставимости масштабов; score не объявляется вероятностью просмотра. Всего **54** контекстно-глобальных вариантов (включая λ=0).
